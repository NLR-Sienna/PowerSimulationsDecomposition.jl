Workflow and validation

Use a branch from main, preserve unrelated/staged changes, and inspect Project.toml, the active manifest, source, tests, and workflows before editing. The dependency upgrade targets PSI 0.38.4 or a compatible patch release. Check extension compatibility against the resolved released source; do not substitute a neighboring development checkout.

Local development cycle

Run the following from the repository root in PowerShell. Use a compatible Julia installation (1.10+). CI selects the latest stable Julia 1.x release with setup-julia's version: '1', not a fixed minor version or the literal string latest. With Juliaup's release channel installed and up to date, use julia +release to select the current stable release locally. Record the actual Julia version in validation reports because the CI selection advances over time.

Step 1: Format

Format Julia source and Markdown using the repository script:

julia -e 'include(joinpath("scripts", "formatter", "formatter_code.jl"))'
git diff --check
git diff --stat

The formatter activates its own environment and modifies the entire checkout. Review changes before staging; preserve unrelated local work. See Formatting for scope and configuration.

Step 2: Test

Test the affected behavior. For example, select the membership and HVDC regressions:

julia --project=. -e 'using Pkg; Pkg.test(; test_args=["test_component_assignment", "test_hvdc"])'

Use julia --project=. -e 'using Pkg; Pkg.test()' to run all enabled test files. Both commands also run the configured Aqua checks; reserve-deliverability tests are enabled. See Tests for the regression-selection table.

Step 3: Prebuild and preview

Prebuild and preview the documentation without deploying:

julia --project=docs -e 'using Pkg; Pkg.develop(PackageSpec(path=pwd())); Pkg.instantiate(); Pkg.status()'
julia --project=docs docs\make.jl
Start-Process .\docs\build\index.html

The strict build executes the dispatch and security-constrained examples and checks documented exports and references. Open the generated site to check navigation, diagrams, and both themes. Keep DOCS_DEPLOY unset; deployment is a separate authorized action. See Build documentation locally for details.

Record commands, Julia/package versions, outcomes, and any unverified checks in the PR. Formatting, passing model tests, and an HTML build verify different surfaces; none substitutes for the others.

Build documentation locally

From the repository root in PowerShell:

julia --project=docs -e 'using Pkg; Pkg.develop(PackageSpec(path=pwd())); Pkg.instantiate(); Pkg.status()'
julia --project=docs docs\make.jl

docs/make.jl uses Documenter 0.27, strict checking, all five exported bindings, and explicit navigation. File-backed @example blocks execute docs/examples/decomposition.jl and docs/examples/security_constrained_reserves.jl. A successful build creates docs/build/index.html. Local builds use non-pretty URLs so pages can also be opened directly. The optional make html target is run from docs, not the repository root.

To run only the example:

julia --project=docs docs\examples\decomposition.jl
julia --project=docs docs\examples\security_constrained_reserves.jl

Diagrams and links

Mermaid fences remain readable on GitHub. Documenter HTML loads pinned Mermaid 11.4.1 from jsDelivr plus docs/src/assets/mermaid.js, which replaces those code blocks with rendered diagrams. The browser needs access to that CDN. Diagrams use a white panel to retain contrast in both Documenter themes. Edit-page links are disabled so local/PR builds do not advertise new pages as already present on main. An HTML build alone does not prove diagrams rendered: inspect the generated pages in a browser, check for SVGs and console errors, and check both light and dark document themes. GitHub's own Mermaid version can differ; inspect the branch Markdown preview separately when available.

Documenter validates local links and @ref targets during the strict build. External services may reject automated link requests; distinguish a verified destination, an inaccessible service, and a confirmed 404 instead of calling all three valid.

CI and deployment

The documentation workflow builds on PRs and pushes to main, release branches, and tags, then uploads the HTML site as an artifact. It also supports manual execution. Build-only checks need no write credentials.

docs/make.jl retains an opt-in DOCS_DEPLOY=true path for authorized maintainers, targeting github.com/NLR-Sienna/PowerSimulationsDecomposition.jl.git, gh-pages, development branch main, development URL dev, and tagged stable/version URLs. The workflow enables that path only when the repository Actions variable DOCS_DEPLOY equals true, for pushes or manual runs on main or version tags beginning with v. PRs and release branches never deploy. Previews are disabled. The deploy step explicitly fails if enabled without its required DOCUMENTER_KEY secret.

One-time administrator setup

The deployment audit found Pages disabled and no gh-pages branch. The account performing that audit had push permission, not repository-administration permission. The following steps require a repository administrator:

  1. Generate a dedicated SSH deployment key using the Documenter 0.27 SSH-key instructions. Generate and handle the private key locally; never paste it into an issue, PR, source file, or build log.
  2. In Settings > Deploy keys, add the public key with Allow write access. In Settings > Secrets and variables > Actions > Secrets, add the base64-encoded private key as the repository secret DOCUMENTER_KEY. The existing TagBot workflow also references that secret, so check its current configuration before replacing any existing key.
  3. In Settings > Secrets and variables > Actions > Variables, create the repository variable DOCS_DEPLOY with the exact value true. Leave it unset or set to false to keep documentation builds artifact-only.
  4. Merge the reviewed documentation changes into main. Its push workflow builds the manual and deploys the versioned files, creating gh-pages. To retry after setup without another commit, select Actions > Documentation > Run workflow > main.
  5. After the first deployment creates gh-pages, open Settings > Pages. Set Source to Deploy from a branch, choose gh-pages and /(root), and save. Do not choose the separate GitHub Actions Pages-artifact source: this workflow uses Documenter's SSH push to a branch, not deploy-pages.
  6. Verify the Documentation run and GitHub Pages publishing run both succeed. Open https://nlr-sienna.github.io/PowerSimulationsDecomposition.jl/dev/ and check navigation, tutorial output, and the rendered Mermaid diagrams. This is an expected destination after setup, not a claim that it is already published.
  7. For stable documentation, publish an appropriate version tag (for example, v0.1.0 only if that release is intended). The tag must include the docs workflow and build configuration. Documenter creates the version and stable aliases on deployment; stable/ is not expected before a release. TagBot already uses DOCUMENTER_KEY so its tag pushes can trigger workflows.

The equivalent manual workflow command is:

gh workflow run docs.yml --repo NLR-Sienna/PowerSimulationsDecomposition.jl --ref main

The normal local prebuild never sets DOCS_DEPLOY. Enabling publication is separate from validating an HTML build. If deployment fails, inspect its logs for authentication or repository-policy errors instead of granting broad personal-token permissions. Keep the SSH key scoped to this repository.

Tests

The intended clean-package command is:

julia --project=. -e 'using Pkg; Pkg.test()'

The current test runner consumes filenames without extensions through ARGS:

julia --project=. -e 'using Pkg; Pkg.test(; test_args=["test_component_assignment", "test_hvdc"])'

The runner performs Aqua checks before file selection. Reserve-deliverability tests run in the default suite and can be selected explicitly:

julia --project=. -e 'using Pkg; Pkg.test(; test_args=["test_reserve_deliverability"])'

test_component_assignment also launches a fresh Julia process using the active test environment, with PowerSystems imports confined to a module. This covers device/branch lookup, regional model pruning, and injector/bus validation without relying on imports into Main. A nested module in the main test process alone would not reproduce this context: the harness already imports PowerSystems into Main.

test/Project.toml declares PowerSystemCaseBuilder, HydroPowerSimulations, StorageSystemsSimulations, TimeSeries, HiGHS, JuMP, Aqua, and the other test prerequisites. Prefer Pkg.test() so the test project and package under test are resolved together; do not assume julia --project=test recreates that sandbox. Report resolver/import failures separately from model assertions and never edit installed dependencies to make a test pass.

Formatting

The repository's formatter command, run from the root, is:

julia -e 'include(joinpath("scripts", "formatter", "formatter_code.jl"))'

It activates its own JuliaFormatter environment and formats the whole repository, including Markdown. Inspect the diff and never discard unrelated user changes. For documentation-only edits, use a targeted format invocation with the options in that script rather than inadvertently reformatting all computational source. Follow .editorconfig and the style guide.

Run git diff --check for whitespace errors. Record exact validation commands, outcomes, resolved dependency versions, and remaining blockers in the pull request, following CONTRIBUTING.md and the PR template.
